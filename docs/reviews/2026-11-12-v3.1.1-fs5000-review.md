# Rad Pro v3.1.1 — Bosean FS-5000 플래싱 전 코드 리뷰

- 대상: 태그 `3.1.1`, FS-5000 빌드(`env:bosean-fs5000-*`)에서 컴파일되는 코드
- 방법: 리드가 전체를 읽고, Opus(측정·시스템 로직)·Sonnet(HAL·UI)·Codex(전체)가 독립 리뷰한 뒤 서로의 발견을 반증하도록 교차 검증
- 한계: 이 PC에는 ARM 툴체인이 없어 **빌드·바이너리 크기·실기 동작은 확인하지 못했다.** 아래는 모두 정적 분석과 계산·시뮬레이션 결과다.

## 결론

플래싱 자체를 막을 결함(부팅 불가, 플래시 영역 겹침, 클럭·워치독 설정 오류)은 찾지 못했다. 다만 v3.1.1 태그 그대로는 데이터 로그 결함 네 건이 남는다. 이 네 건은 저장소 HEAD(`0275cb3`)에서 이미 고쳐져 있으므로 **태그가 아니라 HEAD를 빌드해 올리는 편이 낫다.**

기본 설정(Adaptive fast 평균, 10분 로깅, M4011)으로만 쓰면 아래 major 항목 대부분은 겪지 않는다.

## 플래싱 전 확인할 것

| 항목 | 내용 |
|---|---|
| 서명 | `tools/sign.py`로 서명한 이미지만 올린다. 서명 없는 `firmware.bin`은 전원을 켤 때마다 체크섬 오류 화면과 경보가 뜬다 (`power.c:168`). |
| 언어 빌드 전환 | 영어 빌드는 `FIRMWARE_SIZE=0xd000`, 한국어 빌드는 `0x14000`이라 설정·로그 영역 주소가 다르다. 언어를 바꿔 올리면 설정·누적 선량·튜브 수명이 초기화되고 기존 로그 일부가 덮인다. |
| 배터리 전압 | 올린 직후 통계 화면의 배터리 전압을 멀티미터와 비교한다. ADC 기준전압 채널을 켜는 순서(`stm32_adc.c:108-121`)가 칩 규칙에 맞는지 문서로 확정하지 못했다. |
| LED·핀맵 | `docs/devices/Bosean FS-5000/peripherals.md`와 `fs5000.h`의 PWR_BAT·PULSE_LED·ALERT_LED 핀이 서로 다르다. 문서가 낡았을 가능성이 높지만 LED가 뒤바뀌지 않았는지 본다. |

## 반박되어 뺀 항목

| 주장 | 판정 |
|---|---|
| 긴 문자열이 `draw.c`의 128바이트 버퍼를 넘침 | 길이 검사가 없는 것은 사실이나, 전 언어 문자열을 바이트 단위로 계산한 결과 가장 긴 문단이 93바이트(ru), 한국어는 83바이트라 넘치지 않는다. |
| `gpio_set`/`gpio_clear`와 부저 인터럽트의 경쟁 | 메커니즘은 있으나 FS-5000 호출 경로는 SysTick 안이거나 `syncTick` 직후라 겹치지 않는다. |

## 확인하지 못한 의심

| 의심 | 근거와 막힌 지점 |
|---|---|
| 플래시 쓰기 중 전원이 끊기면 재부팅 루프 | 부팅 때 그 위치를 읽는 것과, 워치독 리셋 뒤 `initPower(true)`가 전원을 붙잡는 것은 코드상 사실이다. 그 위치를 읽을 때 NMI가 나는지는 칩 매뉴얼 기억에만 의존하고, 스타트업 코드가 저장소 밖이라 기본 NMI 핸들러를 보지 못했다. |
| 플래시 지우기·쓰기 중 펄스 누락 | 페이지 지우기 약 20~25 ms 동안 CPU가 멈춘다. 그동안 들어온 펄스는 1개로 합쳐진다. 고계수율에서만 의미 있고 실측이 필요하다. |
| `flash_erase`가 예약 비트에 1을 씀 | `stm32-ext.h:864-866`이 절대주소를 마스크 없이 넣는다. 페이지 번호는 맞게 들어가고 실기에서 동작하는 것으로 보인다. |
| 부트로더 진입 시 워치독 | `startBootloader()`가 워치독을 멈추지 않고 ROM으로 넘어간다. ROM의 처리를 확인하지 못했다. |
| 체스 유효 수 버퍼(181개) | 한도를 넘어도 개수를 계속 센다(`mcu-max.c:522`). 182개 이상인 국면을 재현하지 못했다. |
| LSE가 뜨지 않으면 스플래시에서 무한 대기 | `stm32_rtc.c:25-27`. 수정 부품 고장일 때만 해당. |

## 개선 제안

1. 설정을 두 페이지에 번갈아 쓰고 주기적으로 저장한다. 지금은 정상 전원 끄기 때만 저장해서 워치독 리셋이나 방전 시 그 세션의 누적 선량·튜브 수명·설정 변경을 잃는다. (#8)
2. `closeComm()`에서 로그 읽기를 끝낸다. (#5)
3. 고정 평균에도 신뢰구간 검사를 적용하고, 분모를 창의 끝 시각으로 바꾼다. Opus 시뮬레이션에서 편향이 거의 사라지고 거짓 경고가 약 1/10로 줄었다. (#6)
4. `NVIC_SetPriority`에 0~15 범위의 값을 넘긴다. (#11)
5. 저전압 차단을 한 번의 측정이 아니라 연속 몇 회로 판단한다. 부저·진동·백라이트 순간 부하로 전압이 잠깐 내려갈 수 있다.
6. 로그 버퍼는 8바이트가 찰 때만 플래시에 쓴다. 10분 주기면 최대 약 70분이 RAM에만 있다. 다운로드 직전에 비우는 것을 검토한다.
7. 평균의 "무제한"은 실제로 30일에 끝난다(`average.c:32`). 표기를 맞춘다.
8. `initRTC()`의 LSE 대기에 시간 제한을 둔다.

## 문제없다고 확인한 것

- 클럭: HSI16 ×8 ÷2 = 64 MHz, 플래시 대기 3, APB 4 MHz, SysTick 1 kHz
- 워치독 약 1초, 긴 작업(추이 로딩, 체스 탐색)에 갱신 경로 있음
- 플래시 배치: 펌웨어 `0x08000000–0x0800CFFF`, 설정 `0x0800D000–D7FF`, 로그 `0x0800D800–0x0803FFFF`(101페이지), 겹침 없음
- `sign.py`의 CRC가 STM32 하드웨어 CRC와 일치
- 틱 카운터 wrap, 로그 항목의 페이지 경계·8바이트 정렬, 통신 버퍼(64바이트) 사용량
- 선량 단위 환산, 선원 보정 표, 설정 비트필드 범위 검증
- 배터리 전압 공식, RTC BCD 변환과 읽기 순서
